# Delivery logging on mobile — what is missing, and why

The `message_delivery` table (migration 0011) and the client that fills it were
built for the web app. This is the list of what a mobile release has to add,
written while the decisions were fresh rather than rediscovered later.

The short version: the *measurement* is portable, the *plumbing around it* is
not. Visibility is computed in Dart from scroll geometry and render boxes, so
it behaves identically on both platforms. Everything below is a place where the
surrounding machinery assumes a browser.

## Why the visibility check itself already works on mobile

Worth stating, because the obvious web implementation would not have ported.

The app renders through Flutter's canvas on web, so a chat bubble is not a DOM
element — there is nothing for `IntersectionObserver` to observe, and the
browser-native approach was never available. The check is therefore done the
Flutter way: the bubble's `RenderBox` against the scroll viewport's extent,
plus `AppLifecycleState`. Both are platform-agnostic. This was forced by the
web renderer rather than chosen for portability, but the effect is the same and
the mobile port inherits it.

## 1. `visit_id` does not exist

`message_delivery.visit_id` is the browser page load — generated by the beacon
in `web/index.html` and held in a plain variable for the life of that load, and
the key that joins these rows to `site_visits` and, since migration 0007, to
`conversation_logs`.

It is captured when the bubble's intent is recorded, not when the receipt is
flushed, and that distinction now matters: the beacon stopped reusing an id
across reloads (it was writing a second arrive and leave under the same id and
multiplying the admin joins). So a receipt that survives a reload and lands
afterwards still names the page load it was actually drawn in, which is the
answer the join wants.

A mobile app has no page load. The column is nullable and mobile rows will
carry NULL, which means **every admin query that groups by visit silently
excludes mobile traffic** — it will not error, it will just under-report.

Needed: a session concept for mobile — a fresh id per foreground run, reset
after some idle threshold — written into the same column, or a sibling column
if mixing the two would confuse the existing funnel queries. Decide before the
first mobile release, because backfilling a session id after the fact is not
possible.

## 2. Connection type comes from a browser API

`connection_type` is read from `navigator.connection.effectiveType`. There is
no equivalent in `dart:io`.

Needed: `connectivity_plus` (or similar) for the wifi/cellular distinction.
Note it is not the same measurement — `effectiveType` is an estimate of
observed throughput (`4g`, `2g`), while the plugin reports the interface kind.
Do not write both into one column expecting to group across them; that is the
mistake migration 0005 exists to correct.

## 3. Flush-on-exit has no equivalent

The queue's last chance to drain on web is `visibilitychange` / `pagehide` plus
`navigator.sendBeacon`, which the browser delivers even as the tab closes.

Mobile has nothing comparable. `didChangeAppLifecycleState` fires on the way to
the background, but an HTTP request started there can be suspended or killed
before it completes — and on iOS the process may be terminated outright with no
further callback. A force-quit is silent on both platforms.

Consequence: the mobile queue must be durable across process death and flush on
next launch. This is already how the web queue behaves (it persists rather than
holding rows in memory precisely so a crash does not lose them), so the
mechanism carries over — but on mobile it stops being a safety net and becomes
the primary delivery path, and the "queued_ms" numbers will be much larger as a
result. Any alerting threshold tuned on web data will need re-tuning.

## 4. Background execution limits change what "instantly" means

On web, a receipt POST goes out as soon as the bubble is seen. On mobile, if
the user backgrounds the app mid-reply, the remaining sends are subject to OS
throttling and may be deferred indefinitely.

The rows still arrive eventually, so the intended-vs-seen diff stays correct.
But per-bubble latency stops being meaningful as a delivery-health signal on
mobile, and a dashboard that reads it as one will show a permanent false
problem. If latency matters there, it needs to be measured only for rows sent
while the app was in the foreground.

## 5. Privacy disclosure is a store-review gate

The web app already stores message text server-side in `conversation_logs`, so
this table is not a new category of data. On mobile it becomes a filed
declaration: App Store privacy manifest and Play Data Safety both need to
cover message content, approximate location (the `country` column, derived from
the request), and device/locale fields.

Not a code change, but it does gate release, and it is the item most likely to
be discovered late.

## 6. `country` and `colo` are unaffected

Both are filled in server-side from `request.cf` on whichever flush carried the
row. That works the same for any client. The existing caveat still applies and
gets worse on mobile: for a row that sat in the queue, this is the country of
the *flush*, not of the moment the bubble was shown — and a phone is much more
likely than a browser tab to have moved in between.
